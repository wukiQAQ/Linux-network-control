## 1. 背景与目标

**现状**：采集端只能跑在 Linux（`AF_PACKET`）；Windows 客户端 MeTD 必须连一台 Linux 才能看到数据。
这带来两个现实问题：

1. **演示成本高**：看效果必须先准备一台 Ubuntu 虚拟机并跑通网络模式（比赛、答辩、给别人试用的场景最吃亏）；
2. **离线不可用**：没有 Linux 机器、没有 root、没有网卡权限时，整套系统无法运行，也没有"分析已有 pcap 文件"的入口。

**本次目标（已确认方向）**：在**完全保留现有远程模式**的前提下，把它扩展成"可选数据来源"的**双模式**：

- 模式 M1：**远程 Linux**（现状，行为不变）
- 模式 M2：**本机 Windows · 实时采集**（纯 Go 抓本机网卡）
- 模式 M3：**本机 Windows · 离线分析**（导入 pcap/pcapng 文件做分析）

**明确不做（本次范围外）**：

- 不做 payload 内容还原 / 内容级审计（只做会话与元数据分析）；
- 不引入 Npcap / gopacket C 绑定（保持纯 Go、免 CGO 的构建链）；
- 不做 Windows 内核驱动；
- 不改动现有远程模式的接口语义与客户端行为。

## 2. 三种使用形态

| 模式 | 数据来源 | 依赖 | 权限 | 典型场景 | 能力差异 |
| --- | --- | --- | --- | --- | --- |
| **M1 远程 Linux**（现状） | Linux 采集端抓真实网卡 | Linux + 网络可达 | Linux 侧 root/CAP_NET_RAW | 生产监控、多机列表 | 具备全部能力（多队列、CPU 绑定、内核剪枝） |
| **M2 本机 Windows · 实时** | Windows 原始套接字抓本机网卡 | 无额外依赖 | **需管理员** | 无 Linux 机器时看本机流量 | 无多队列、无 CPU 绑定、无内核剪枝；过滤仅用户态 |
| **M3 本机 Windows · 离线** | 导入 pcap/pcapng 文件 | 无 | **无需管理员** | 比赛演示、复盘已有抓包 | 无实时指标口径，其余分析能力一致 |

> M1 的"Linux 本机看网页仪表盘"仍属 M1 形态，不受本次改动影响。

## 3. 架构设计

### 3.1 设计原则：模式差异只落在"数据源"与"谁拉起进程"

采集端仍然是"**一个 HTTP 服务 + 一个数据源**"：解析 → 流表 → 聚合 → 存储 → API → 展示 这六层**完全复用**，不因模式而分叉。
因此模式切换对上层是透明的：客户端永远只是"连一个地址"，区别在地址后面是谁、由谁启动。

```text
Windows 客户端 MeTD
  ├─ M1 远程：HTTP → Linux netmon（AF_PACKET，默认 :8080，可配令牌）
  ├─ M2 本机：拉起随包发布的 netmon.exe（Windows 数据源）→ 连 127.0.0.1:8080
  └─ M3 离线：同一份 netmon.exe 以 replay 模式加载所选 pcap → 连 127.0.0.1:8080
```

### 3.2 为什么不把抓包直接做进 Tauri 客户端

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 抓包做进 Tauri（Rust 侧） | ✗ 不采用 | 解析/流表/聚合/存储/API 全部要重写一遍，且两条实现会长期不一致 |
| **复用采集端进程 + sidecar 启动**（本设计） | ✓ 采用 | 零重复实现；离线与实时共用同一条分析链路；Linux/Windows 行为差异集中在数据源层 |

### 3.3 数据与配置隔离

- 本机模式使用**独立数据目录**（建议 `%LOCALAPPDATA%\MeTD\local-data`），不与远程模式的分析数据混存；
- 界面上明确标注"数据来自本机 / 来自远程 Linux"，避免把两边的数字看串；
- 连接配置新增 `mode` 字段（`remote` / `local` / `offline`），**旧配置缺省按 `remote` 处理**，保证向后兼容。

## 4. Windows 实时采集（M2，纯 Go）

### 4.1 代码结构

```text
internal/capture/live_linux.go     // 现状不动：//go:build linux，AF_PACKET / PACKET_FANOUT / 内核剪枝
internal/capture/live_other.go     // 现状：//go:build !linux，NewLive* 一律返回"live 抓包仅支持 Linux"
internal/capture/live_windows.go   // 待新增：//go:build windows（与 live_other.go 的 tag 互斥）
```

> **更正（v1.1）**：v1.0 这里写成"新增 `live_windows.go`、`capture.go` 按平台选择"，与实际不符。仓库里已存在
> `internal/capture/live_linux.go` 与 `internal/capture/live_other.go`（非 Linux 平台桩：`NewLive` /
> `NewLiveWithReaders` / `NewLiveWithReadersPinned` 都返回 `errors.New(errLiveUnsupported)`，文案为
> "live 抓包仅支持 Linux（可改用 synthetic/replay 数据源）"），`cmd/netmon/main.go` 的 `buildSource`
> 里另有一道 `runtime.GOOS != "linux"` 的兜底判断。实现 M2 时要把 `live_other.go` 的 build tag
> 从 `!linux` 收窄为 `!linux && !windows`，否则两个文件会同时参与 windows 构建而重复定义。

### 4.2 技术路线：Windows 原始套接字 + `SIO_RCVALL`

- 绑定本机地址的 IP 套接字（`net.ListenIP` / `ip4:`、`ip6:`），取 `SyscallConn()` 后通过 `WSAIoctl` 下发 `SIO_RCVALL`，使网卡进入混杂接收；
- **需要管理员权限**（否则 `WSAIoctl` 直接失败）；
- **只能抓该接口/地址上的报文**，不是镜像口，也拿不到交换机侧流量；
- **没有内核 BPF**：现有 `[capture] filter` 表达式只能在用户态过滤（`filter_kernel` 恒为 false）；
- 多队列（`PACKET_FANOUT`）、CPU 绑定（`sched_setaffinity`）在 Windows 上**不存在**，配置项保持可解析但只记一条日志说明被忽略。

### 4.3 能力上报（沿用 features 门控）

新增两项能力，供客户端决定显示哪些面板与提示：

| 能力 | 含义 | 出现条件 |
| --- | --- | --- |
| `source.local` | 支持在本机采集（无需远程 Linux） | Windows 构建 + 管理员权限可用 |
| `capture.offline` | 支持离线 pcap 分析 | replay 数据源可用（两个平台都有） |

不变的是 Linux 专有能力：`capture.multiqueue`、`capture.cpupin`、`capture.filter`（内核剪枝部分仅 Linux）。

### 4.4 权限与失败提示

- 启动时检测管理员权限：不是管理员 → 明确报错并给出"以管理员身份运行"的可操作指引，**不要静默退化成抓不到包**；
- 抓包成功但收不到报文时，客户端提示"本机模式只抓本机接口流量，请确认有流量经过该接口"。

### 4.5 未验证项（必须诚实标注）

- **`SIO_RCVALL` 路线尚未在本机验证**：需要管理员权限才能试探；
- 实现前先做一次 spike：最小程序抓 100~500 个包，确认①能收到本机流量 ②报文长度/时间戳/接口信息够用 ③对系统性能影响可接受；
- spike 结论若不理想，按第 8 节的降级方案处理。

## 5. 离线 pcap 分析（M3，先落地、风险最低）

M3 复用现有 `replay` 数据源，**不需要任何新的采集代码**：

```toml
[core]
source = "replay"
replay_file = "D:\\samples\\demo.pcap"
```

客户端新增"打开 pcap 文件"入口：选择本地文件 → 以该文件启动本地采集进程 → 与 M1/M2 完全相同的分析界面。
这条路的优势：**零权限、零依赖、可离线演示**，测试也天然稳定（可准备一个含 DNS/HTTP/TLS 的小 pcap 作为固定样例）。

**当前已可直接使用（采集端 0.23.4 + 仓库内脚本）**：不装客户端也能跑通 M3——

```powershell
.\deploy\windows\build-netmon.ps1                          # 构建 Windows 版引擎（一次，产物 bin\netmon.exe，不入库）
.\deploy\windows\start-local-analysis.ps1 -Pcap demo.pcap  # 启动本机引擎 + 打开浏览器仪表盘
.\deploy\windows\start-local-analysis.ps1 -Stop            # 按 pid 文件停止
```

脚本会：校验 pcap 文件 → 检查端口占用 → 用
`-replay-file <pcap> -offline -data-dir %LOCALAPPDATA%\MeTD\local-data -listen 127.0.0.1:<port>`
拉起 `netmon.exe` → 轮询 `/api/v1/health` 就绪 → 打印「采集端版本 / 数据源 / 平台 / 数据时间」与 TOP 3 概览 → 打开浏览器。
这套参数契约与客户端 sidecar（`client/src/localsource.js` 的 `localEngineArgs`）**完全一致**，两条路不会分叉。

## 6. 客户端（MeTD）交互设计

1. 连接页/启动页新增**数据来源三选一**：`远程 Linux` ｜ `本机 Windows（实时）` ｜ `离线 pcap 文件`；
2. 本机模式提供 **启动本机采集 / 停止本机采集**（Tauri sidecar 管理子进程生命周期，不经 HTTP）；
3. 顶部状态区显示当前模式与数据来源；本机模式额外显示**能力差异横幅**（"本机模式不支持多队列与内核剪枝，过滤仅在用户态生效"）；
4. 模式切换时清空/切换数据集，避免远程与本机数字混淆；
5. 权限不足时给出引导，而不是"连接成功但没数据"。

## 7. 接口与配置变更（草案）

| 变更 | 位置 | 说明 |
| --- | --- | --- |
| 复用 `source` 字段 | `GET /api/v1/traffic/now` | 已存在（`synthetic` / `replay` / `live`），本机模式回报 `live`，客户端据 features 判断平台差异 |
| 新增 `os` 字段 | `GET /api/v1/traffic/now` | **已实现（采集端 0.23.4）**：`runtime.GOOS`，客户端据此识别本机引擎所在平台 |
| 新增能力 | `internal/buildinfo/buildinfo.go` | **已实现**：`capture.offline`（可离线回放 pcap）。`source.local` **暂不声明**——M2 未实现，声明了会变成"点了没反应的入口" |
| 连接配置新增字段 | 客户端 `profiles.js`（localStorage） | **已实现（客户端 0.13.0）**：`mode`，缺省 `remote`，旧配置不受影响 |
| 采集端命令行 | `cmd/netmon` | **已实现（采集端 0.23.4）**：`-config`（原有）、`-replay-file`、`-offline`、`-data-dir`（同时把 `sqlite_path` 挪进该目录）、`-listen` |

> 原则：**不引入仅为本机模式服务的新 REST 接口**。模式差异用"配置 + features"表达，避免接口矩阵膨胀。

## 10. 风险与未定项

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| `SIO_RCVALL` 抓包效果未验证 | M2 可能整体不可用 | 先 spike；失败即走降级方案 |
| 管理员权限门槛 | 影响"双击即用"体验 | 明确提示 + 文档引导；M3 作为零权限替代路径 |
| 抓包范围与用户预期不符 | 被误判为"系统坏了" | 界面明确"只抓本机接口流量" |
| 多平台行为差异 | 文档/测试容易漏 | 能力矩阵写进功能清单；双平台编译纳入 CI 式检查 |
| 存储增长（离线分析大 pcap） | 本地 SQLite 膨胀 | 沿用保留策略；后续按 Backend 接口换外部分析库 |

## 11. 待评审决策点

1. 本机模式的数据目录与远程模式**是否共用 SQLite 文件** —— **已定：不共用**（2026-10-08 确认，本机模式用独立数据目录与独立库，避免两套数字互相污染）；
2. 客户端 0.13.0 的"数据来源"是否放在**连接页** —— 待客户端实现时最终确认（本设计建议放连接页，与"连哪台机器"同级）；
3. 是否接受"本机模式功能少于远程模式"这一现实 —— **已定：接受**，并在界面显式说明；
4. M2 spike 的验收门槛：本机接口在一个采集周期内能稳定收到 ≥95% 的预期报文（用于判断是否继续）—— **待 spike**。
