# Linux 网络流量监控系统 —— 技术方案

> 版本：v0.1  
> 日期：2026-09-02  
> 关联文档：[产品设计文档](产品设计文档.md)、[系统设计文档](网络流量监控系统设计文档.md)  
> 结论先行：**数据侧与服务端用 Go，展示侧用 Web（Vue 3 + TypeScript + ECharts），现阶段不做桌面客户端（不用 Electron）**，为多机对比、插件化、单位切换预留扩展点。

## 1. 技术选型总览

### 1.1 分层与选型

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| 采集 / 数据侧 | Go（libpcap 起步，后续 AF_PACKET / eBPF） | 需要 root 直读网卡，单二进制、并发模型契合抓包管道 |
| 服务端 | Go（net/http） | 与采集同进程，MVP 单进程单二进制 |
| 存储 | SQLite（MVP）→ InfluxDB / ClickHouse（多机后） | 单机零运维，多机后按规模升级，接口抽象可替换 |
| 展示侧 | Vue 3 + TypeScript + Vite + ECharts | 组件化适合仪表盘与后续插件化；ECharts 原生支持多序列对比 |
| 实时通道 | MVP 轮询 → V2 WebSocket | 实时性需求到达后再引入 |
| 部署 | 前端产物 `go:embed` 进 Go 二进制 + systemd | 保持"单二进制、零客户端安装"的产品形态 |

### 1.2 关于桌面客户端（Electron）的结论

讨论结论：**现阶段不引入 Electron，展示侧保持 Web 应用**。原因：

- 产品定位是"Linux 守护进程 + 浏览器访问即用"，数据在远程机器上，桌面壳没有增量价值；
- Electron 体积大（百 MB 级）、内存占用高，多机对比、插件、单位切换均为 Web 技术可覆盖的能力；
- 若未来确有"本地桌面总控台"需求，优先评估 Tauri（体积小），Electron 仅在团队纯 JS 栈时作为妥协方案。

## 2. 总体架构

### 2.1 单机形态（MVP）

```text
┌────────────────── netmon 单进程（Go） ──────────────────┐
│  capture → parser → flowtable → aggregator              │
│                    │ 指标 / 流记录                       │
│                    ▼                                    │
│              storage（SQLite）                          │
│                    ▲                                    │
│    REST API ← 查询 / 写入指标流                          │
│    go:embed 静态页面（Vue 3 构建产物）                    │
└──────────────────────┬──────────────────────────────────┘
                       │ 浏览器访问 :8080
                       ▼
            仪表盘（对比、插件、单位切换均在此层）
```

### 2.2 未来多机形态（演进目标，不在 MVP 实现）

```text
┌─ Linux A ─┐   ┌─ Linux B ─┐
│ netmon    │   │ netmon    │
│ Agent 模式│   │ Agent 模式│
└─────┬─────┘   └─────┬─────┘
      │ 指标上报（HTTPS/消息队列）│
      └────────┬──────┘
               ▼
      ┌── Server 汇聚服务 ──┐
      │ 时序存储 / 告警 / API │ ← 前端（多机对比选择器）
      └──────────────────────┘
```

架构演进依赖三个预留点（MVP 阶段就要埋好）：

1. 所有指标与流记录携带 `machine_id` / 网卡标签，即使单机也写入该字段；
2. 存储层抽象 `Storage` 接口，SQLite 实现与未来时序库实现可替换；
3. API 路径按资源设计（`/api/v1/machines/...`），便于未来挂多机查询。

## 3. 后端技术方案

### 3.1 代码结构（Go）

```text
cmd/netmon/            # 入口：配置加载、装配各层、启动 HTTP
internal/capture/      # 采集：接口 CaptureSource，libpcap 与 pcap 回放实现
internal/parser/       # 协议解析：以太网 / IPv4 / TCP / UDP
internal/flow/         # 流表：5 元组聚合、双向归并、双超时过期
internal/aggregator/   # 1s tick 聚合：bps / pps / 并发连接
internal/storage/      # Storage 接口 + SQLite 实现
internal/api/          # REST 路由与处理器（/api/v1/...）
internal/config/       # TOML 配置解析
web/                   # 前端源码（Vue 3），构建产物 embed 进二进制
```

### 3.2 关键选型说明

- **采集**：MVP 用 `libpcap`（含 pcap 文件回放实现，测试依赖它）；性能优化期再实现 `AF_PACKET + PACKET_MMAP`，两者都实现 `CaptureSource` 接口，切换不触碰上层。
- **单位存储**：后端一律存储**原始值**（字节、包数、时间戳），不做单位换算，保证精度与可迁移；换算完全交给前端展示层。
- **时间与 ID**：时间统一 UTC 存储、前端本地化显示；指标用 `series + tags(含 machine_id) + ts + value` 模型，天然适配未来时序库。
- **接口版本化**：所有对外接口前缀 `/api/v1`，前端只消费版本化 API，后端重构不影响界面。

### 3.3 核心 API 草案（MVP）

```text
GET /api/v1/traffic/now       # 当前实时指标
GET /api/v1/traffic/history   # 历史曲线（from/to/step）
GET /api/v1/sessions          # 会话列表（分页 + 过滤）
GET /api/v1/health            # 自身健康（收包/丢包/流表大小）
```

## 4. 前端技术方案

### 4.1 选型

- **框架**：Vue 3 + TypeScript + Vite（构建快、组件模型适合面板化界面）。
- **图表**：ECharts——多序列对比、大数据量下 canvas 渲染、格式化器可定制。
- **状态**：Pinia；全局"显示设置"（单位制式、刷新频率）作为跨页面状态。
- **组件拆分**：`TimeRangePicker`、`TrafficChart`、`SessionTable`、`HealthPanel`、`MachineSelector`（V2 起）等，与后端 API 一一对应。

### 4.2 单位切换设计

- 展示层维护一份**单位设置**：速率单位制（bit/s 十进制 / Byte/s / 二进制 Ki/Mi）、包速率、字节容量、时间格式；
- 数据管道固定为"后端返回原始数值 → 前端格式化函数统一渲染"，格式化逻辑收敛在 `formatters.ts` 单一模块；
- 切换设置即时生效并持久化到本地（localStorage），后续可同步到服务端用户配置。

### 4.3 插件化设计方向（V2/V3，不在 MVP 实现）

- **界面插件**：以"面板"为单位，每个面板 = 清单（标题、类型、数据源绑定、参数 schema）+ 渲染组件；渲染组件用 **Web Components** 注册，宿主页面按清单动态挂载，实现插件不重新编译主程序即可加载；
- **数据侧插件**：新采集源 / 分析器（如 NetFlow 源、DPI 模块）以**独立进程 + 定义好的插件协议（gRPC/HTTP + 配置）**接入，主程序通过进程管理加载/卸载；不使用 Go 原生 plugin 机制（版本耦合脆弱）；
- 插件市场与签名校验等治理能力放到更晚版本。

## 5. 多机对比的设计方向（V2/V3）

- 前端只需"机器多选 + 同指标多序列对比图"，ECharts 原生支持；
- 真正的工程量在后端：Agent 采集 → 上报（HTTPS 或消息队列）→ Server 汇聚 → 时序存储 → 对比查询 API；
- 指标模型从 MVP 起就带 `machine_id` 标签，未来对比查询 = 按标签过滤的多序列查询，无需改动数据管道。

## 6. 测试与验证策略

| 层 | 手段 |
| --- | --- |
| Go 单元测试 | 解析、流表、聚合、存储各模块 `go test` |
| 链路测试 | pcap 文件回放，离线验证"采集 → 查询"全链路 |
| 前端 | Vitest 组件测试（格式化、面板渲染、状态）；后续 Playwright E2E |
| 交付前 | `go build ./...` + `go vet ./...` + `go test ./...` 全部通过，前端构建成功 |

## 7. 版本落地映射

| 版本 | 技术任务 |
| --- | --- |
| MVP | Go 单进程全链路 + Vue3 仪表盘（单位切换基础版）+ pcap 回放测试 |
| V2 | 告警、TOP N、WebSocket、鉴权、多队列抓包、界面插件框架 |
| V3 | Agent + Server 架构、多机对比、NetFlow 接入、eBPF 加速、数据侧插件协议 |
