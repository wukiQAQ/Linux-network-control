## 1. 项目概述

### 1.1 背景与目标

本系统运行于 Linux 平台，用于对网络流量进行持续、实时的监测与分析。系统需要回答三类问题：

1. **当前网络状况**：总带宽、包速率、并发连接数等实时指标；
2. **流量构成**：哪些主机/IP 之间在通信，使用哪些端口和协议，各占多少流量；
3. **异常发现**：带宽突增、连接数异常、疑似扫描等行为能够被规则引擎识别并通知。

### 1.2 监控粒度

系统按四级粒度组织数据，由粗到细：

| 粒度 | 说明 | 典型查询 |
| --- | --- | --- |
| 网卡级 | 整块网卡的总收发流量 | 实时带宽曲线 |
| 主机级 | 按源/目的 IP 聚合 | TOP N IP 流量排行 |
| 会话级 | 按 5 元组（源/目的 IP、端口、协议）聚合 | 单条连接状态与流量 |
| 应用级 | 基于端口或 DPI 识别应用协议 | 协议占比（HTTP/DNS/...） |

首版以会话级为核心，网卡级和主机级由会话数据聚合得出；应用级（DPI）作为后续增强项。

### 1.3 核心需求

- **实时性**：秒级延迟展示当前流量，毫秒级数据采集；
- **可靠性**：监控系统自身必须暴露丢包率，抓包缓冲溢出不能无声无息；
- **可扩展性**：采集、存储、展示各层通过接口解耦，后端可替换，规模可增长；
- **低侵入**：仅需 root / `CAP_NET_RAW` 权限抓包，不改动内核与业务系统；
- **可测试性**：支持 pcap 文件回放，脱离真实网络即可开发与回归验证。

## 2. 总体架构

### 2.1 分层架构

```
┌──────────────────────────────────────────────┐
│ 展示层   Web 仪表盘 / Grafana / CLI          │
└──────────────────┬───────────────────────────┘
                   │ HTTP + WebSocket
┌──────────────────▼───────────────────────────┐
│ 服务层   REST API / 实时推送 / 配置管理       │
└──────┬───────────────────────┬───────────────┘
       │                       │
┌──────▼────────┐     ┌────────▼────────┐
│ 统计聚合层      │     │ 告警引擎          │
│ bps/pps/TopN  │     │ 规则/防抖/通知    │
└──────┬────────┘     └─────────────────┘
       │
┌──────▼──────────────────────────────────────┐
│ 存储层   时序指标 / 流记录 / 保留策略         │
└──────┬──────────────────────────────────────┘
       │
┌──────▼──────────────────────────────────────┐
│ 解析层   协议解码 / 5元组流识别 / 流过期      │
└──────┬──────────────────────────────────────┘
       │ 原始包（环形缓冲）
┌──────▼──────────────────────────────────────┐
│ 采集层   AF_PACKET / libpcap / eBPF /       │
│         NetFlow 接收                        │
└─────────────────────────────────────────────┘
```

### 2.2 核心数据流

```
网卡 → 抓包 → 协议解析 → 流表聚合
                              ├─→ 定时指标（1s）→ 存储 + WebSocket 推送
                              └─→ 过期流记录（5min）→ 存储
                                                        ├─→ REST 查询 → 展示
                                                        └─→ 告警引擎 → 通知
```

数据流遵循"生产者—消费者"管道模型：采集层是唯一的生产者，解析、聚合、存储逐级消费。每一层只依赖下一层的接口，层与层之间通过通道（channel）传递不可变数据，便于并发扩展与单元测试。

### 2.3 设计原则

1. **分层解耦，接口驱动**：采集方式、存储后端、告警通道均可替换，替换不影响其他层；
2. **增量聚合，定时快照**：指标只做增量累加，按固定 tick 输出快照，禁止全量重算；
3. **数据分级**：高精度原始数据短留，低精度聚合数据长留；
4. **缓冲与背压**：各层之间使用有界缓冲，满则丢弃并计数，防止内存失控；
5. **自身可观测**：系统健康指标（收包数、丢包数、处理延迟）与业务指标一同暴露。

## 4. 模块设计

### 4.1 采集层（Capture）

**职责**：从目标网卡抓取原始数据包，或接收网络设备导出的 NetFlow/sFlow；将"读包"与"业务处理"解耦，向解析层提供统一的数据包来源。

**实现方式**：

- 首选 `AF_PACKET + PACKET_MMAP`：`socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL))`，通过 mmap 映射内核环形缓冲区实现近零拷贝收包，性能好、无第三方依赖；
- 开发期可切换 `libpcap`：封装了抓包细节，支持过滤表达式（BPF）与 pcap 文件回放，便于调试；
- 高负载场景演进到 `eBPF (XDP)`：在驱动层完成收包、过滤、采样，用户态只接收摘要，性能最高；
- 对接交换机时可另开 NetFlow v9 / IPFIX 监听器（UDP 2055/9995），解析流记录，不抓原始包。

**关键难点**：

- 多队列网卡按队列分配到多个收包协程，绑定 CPU 提升缓存命中率；
- 环形缓冲溢出时内核会丢包，必须通过 `PACKET_STATISTICS` 读取丢包计数并暴露；
- 抓包缓冲大小（`PACKET_RX_RING` 块数）需根据网卡速率调优。

**对外接口**：

```go
type CaptureSource interface {
    Open(iface string, opts CaptureOptions) error
    Next() (*Packet, error)        // 阻塞式取包
    Stats() CaptureStats           // 收包数 / 丢包数 / 缓冲占用
    Close() error
}

type CaptureOptions struct {
    BufferBytes  int               // 环形缓冲大小
    Promiscuous  bool              // 混杂模式
    BPFFilter    string            // 可选 BPF 过滤
    SnapshotLen  int               // 截断长度
    QueueBinding bool              // 是否按队列绑定
}
```

### 4.2 解析层（Parser）

**职责**：从原始字节中逐层剥离链路 / 网络 / 传输层头部，提取 5 元组，将双向数据包归并为会话流，维护流状态。

**实现方式**：

- 手工解析以太网帧 → IPv4/IPv6 → TCP/UDP/ICMP 头部，获取源/目的 IP、端口与协议号；
- 5 元组归一化：A→B 与 B→A 方向归并为同一条流，`FlowKey` 内部按固定规则排序（如源地址字典序），同时保留"发起方向"标记；
- 流表为并发安全的哈希表，key 为 `FlowKey`，value 为 `Flow` 状态（包数、字节数、起止时间、TCP 标志位）；
- 流过期采用双超时：空闲超时（默认 30s，TCP 会话可延长）+ 硬超时（默认 5min），到期流交给下游导出，防止流表无限膨胀。

**关键难点**：

- 分片 IP 包需要按分片 ID 重组后才能识别传输层端口（首版可标记"未识别"并跳过）；
- TCP 半连接、SYN 洪泛等状态下流的生命周期判断；
- 流表大小上限与淘汰策略（LRU + 超时）结合，防止恶意流量打爆内存。

**对外接口**：

```go
type FlowKey struct {
    SrcIP, DstIP     netip.Addr
    SrcPort, DstPort uint16
    Protocol         uint8
}

type Flow struct {
    Key        FlowKey
    Start, End time.Time
    Packets    uint64
    Bytes      uint64
    TCPFlags   uint8
    Direction  Direction           // 发起方向
}

type FlowTable interface {
    Lookup(key FlowKey) (*Flow, bool)
    Upsert(key FlowKey, pkt *Packet)   // 更新计数与时间
    Expire(now time.Time) []*Flow      // 返回过期流
    Size() int
}
```

### 4.3 统计聚合层（Aggregator）

**职责**：把海量包 / 流数据压缩成可查询的指标：总带宽（bps）、包速率（pps）、并发连接数、TOP N 会话 / IP / 端口、协议分布。

**实现方式**：

- 固定 tick（1 秒）驱动增量聚合：累加包数与字节数，输出"瞬时速率"时序点；
- 长周期指标（1min / 5min）通过滑动窗口或降采样得出，不重复扫描原始包；
- TOP N 使用最小堆维护前 K 个元素，避免全量排序；
- 聚合结果同时路由到三个下游：存储层（持久化）、WebSocket 广播（实时展示）、告警引擎（规则判定）。

**关键难点**：

- 速率计算要正确处理重启 / 跳变：两次快照之间计数器回退时按重置处理；
- 聚合 tick 与流过期事件不同步，需要以时间戳对齐而非依赖到达顺序；
- 内存与实时性折中：聚合窗口越大占用越高，需按保留策略降采样。

**对外接口**：

```go
type MetricPoint struct {
    Series string            // 如 "traffic.bps"、"traffic.conns"
    Tags   map[string]string // 如 {iface: eth0, ip: 10.0.0.1}
    Ts     time.Time
    Value  float64
}

type Aggregator interface {
    Tick(now time.Time) []MetricPoint
    TopN(now time.Time, n int) []TopEntry
    Subscribe() <-chan []MetricPoint   // 实时广播
}
```

### 4.4 存储层（Storage）

**职责**：持久化两类数据——时序指标（带宽曲线等）与流记录（会话详情），并执行保留策略。

**实现方式**：

- 首版 SQLite：单文件、零运维，适合单机小规模；指标与流记录分表存储，写入批处理（批量 INSERT）；
- 完整版 InfluxDB：专为时序设计，支持连续查询与自动保留策略；
- 大规模 ClickHouse + Kafka：流记录批量落盘，适合海量查询分析；
- 通过 `Storage` 接口抽象，后端可替换；写入走异步队列，避免阻塞聚合层。

**关键难点**：

- 写入吞吐：必须批处理 + 定时 flush，不能每包一写；
- 保留策略分桶：原始 1s 粒度保留 7 天，1min 聚合保留 30 天，1h 聚合保留 1 年；
- 查询能力抽象：时序查询与流查询语义不同，接口需分别定义。

**对外接口**：

```go
type Storage interface {
    WriteMetric(m MetricPoint) error
    WriteFlow(f FlowRecord) error
    QueryMetrics(series string, tags map[string]string,
                 from, to time.Time, step time.Duration) ([]MetricPoint, error)
    QueryFlows(filter FlowFilter, limit int) ([]FlowRecord, error)
    Close() error
}
```

### 4.5 服务层（API）

**职责**：对外提供查询与实时订阅能力：REST 查询历史 / 当前指标、流记录、TOP N；WebSocket 实时推送指标流。

**实现方式**：

- `net/http` 提供 REST 接口，接口版本化（`/api/v1/...`）；
- 查询参数统一支持时间范围、聚合粒度、过滤条件（IP、端口、协议）；
- WebSocket 通道订阅聚合层广播流，不轮询存储层；
- 可选的简单鉴权（令牌）与限流，防止被滥用。

**核心接口**：

```
GET /api/v1/traffic/now            # 当前实时指标
GET /api/v1/traffic/history        # 历史曲线，参数 from/to/step
GET /api/v1/flows                  # 流记录查询，参数过滤
GET /api/v1/topn?field=ip&n=10     # TOP N 排行
GET /api/v1/alerts                 # 告警历史
WS  /api/v1/ws/traffic             # 实时指标推送
```

### 4.6 告警引擎（Alerting）

**职责**：消费指标流，按规则识别异常（带宽超限、连接数突增、疑似端口扫描），触发通知并记录历史。

**实现方式**：

- 规则模型：`指标 + 比较条件 + 阈值 + 持续时间`；
- 状态机防抖：条件持续 N 秒才触发告警（避免毛刺误报），恢复后重置状态，支持"恢复通知"；
- 通知通道可插拔：Webhook / 邮件 / 钉钉 / 企业微信；
- 规则存于配置文件，支持运行时热加载；告警事件持久化供查询。

**关键难点**：

- 状态机生命周期：触发 → 持续 → 恢复 → 重置，每个阶段都要正确记录时间戳；
- 同一指标多条规则时的优先级与去重；
- 通知失败重试与防风暴（同类型告警限频）。

**对外接口**：

```go
type AlertRule struct {
    ID          string
    Metric      string
    Operator    string            // ">" ">=" "<" ...
    Threshold   float64
    For         time.Duration     // 持续多久触发
    Notify      []NotifyChannel
}

type AlertEngine interface {
    Evaluate(metrics []MetricPoint) []AlertEvent
    Reload(rules []AlertRule) error
}
```

### 4.7 展示层（UI）

**职责**：将数据可视化：总览带宽曲线、实时会话、TOP N、协议占比、告警列表。

**实现方式**：

- 首版接 Grafana：通过我们的 REST API 作为数据源，节省前端开发量；
- 后续自研 Web 端：Vue/React + ECharts，实时面板走 WebSocket；
- 页面规划：总览仪表盘、流量明细页（按 IP/端口筛选）、告警中心、系统健康页。

### 4.8 配置与部署

**职责**：将网卡、采样率、存储、告警规则等全部配置化，提供 systemd 托管与开机自启。

**实现方式**：

- TOML 配置文件 + 命令行参数覆盖，配置结构见第 6 章；
- 编译为单一二进制，提供 `systemd unit`，`Restart=on-failure`；
- 日志统一走 journald / 文件，按模块打点；系统自身健康指标单独暴露（见 2.3）；
- 权限：安装时赋予 `CAP_NET_RAW`（`setcap cap_net_raw=eip`），避免以 root 常驻。

## 5. 核心接口总览

```go
// 采集层：屏蔽 AF_PACKET / libpcap / eBPF 差异
type CaptureSource interface {
    Open(iface string, opts CaptureOptions) error
    Next() (*Packet, error)
    Stats() CaptureStats
    Close() error
}

type FlowTable interface {

type Aggregator interface {

type Storage interface {
```

## 6. 数据模型

### 6.1 流记录表（Flow Record）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER PK | 自增主键 |
| start_time / end_time | TIMESTAMP | 流起止时间 |
| src_ip / dst_ip | TEXT | 源/目的 IP（v6 用 TEXT） |
| src_port / dst_port | INTEGER | 端口，ICMP 等无端口协议为 0 |
| protocol | INTEGER | IP 协议号（6=TCP, 17=UDP, 1=ICMP） |
| packets / bytes | INTEGER | 双向累计包数 / 字节数 |
| tcp_flags | INTEGER | TCP 标志位掩码 |
| iface | TEXT | 抓包网卡 |

索引：`(start_time, src_ip)`、`(start_time, dst_ip)`、`(start_time, protocol)`。

### 6.2 时序指标表（Metric）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| series | TEXT | 指标名，如 traffic.bps |
| tags | TEXT | JSON 编码的标签（iface、ip 等） |
| ts | TIMESTAMP | 采样时间 |
| value | REAL | 指标值 |

索引：`(series, ts)`。SQLite 首版可用该表；InfluxDB 对应 measurement + tag + field。

### 6.3 告警规则与事件

告警规则（配置文件，不落库）：

```toml
[[alert.rules]]
id = "iface-bandwidth-high"
metric = "traffic.bps"
tags = { iface = "eth0" }
operator = ">"
threshold = 1_000_000_000   # 1 Gbps
for = "30s"
notify = ["webhook-ops"]
```

告警事件表（持久化）：`id`、`rule_id`、`metric`、`value`、`threshold`、`started_at`、`resolved_at`、`status`（firing/resolved）。

## 7. 实现方案与里程碑

### 阶段一：MVP（约 2~3 周）

**目标**：跑通"抓包 → 解析 → 指标 → API → 展示"全链路，能看实时带宽与会话列表。

- 采集：AF_PACKET + PACKET_MMAP 单队列抓包；
- 解析：以太网 + IPv4 + TCP/UDP，流表与双超时过期；
- 聚合：1s tick，总带宽 / pps / 并发连接数；
- 存储：SQLite 批写；
- 服务：REST 查询 + WebSocket 实时推送；
- 测试：pcap 回放验证；
- 验收：`topn`、`traffic/history` 可查询，丢包计数可见。

### 阶段二：完整功能（约 4~6 周）

- 采集：多队列 + CPU 绑定；pcap 文件回放模式正式化；
- 解析：IPv6、ICMP、TCP 状态机（连接建立/关闭计数）；
- 聚合：1min / 5min 降采样，TOP N（IP/端口/协议），协议分布；
- 告警：规则引擎、防抖状态机、Webhook 通知、热加载；
- 服务：分页、过滤、鉴权；
- 存储：保留策略与自动清理；
- 展示：Grafana 仪表盘模板。

### 阶段三：性能与扩展（后续迭代）

- 采集演进 eBPF/XDP，用户态只收摘要；

## 8. 测试与验证方案

1. **pcap 回放**：采集层支持读取 pcap 文件作为数据源，开发与回归不依赖真实网络；准备典型流量样本（Web、DNS、扫描、大流量）；
2. **单元测试**：解析层覆盖各种头部组合（IPv4/IPv6、TCP/UDP、分片、异常包）；聚合层验证速率与 TOP N 正确性；
3. **集成测试**：采集 → 解析 → 存储 → API 全链路，用回放流量比对预期指标；
4. **性能压测**：构造高速流量，验证丢包率、CPU 占用、流表大小，确定单机承载上限（如 1Gbps / 10Gbps）；
5. **健壮性**：流表膨胀、缓冲溢出、后端写入失败时的降级与恢复。

## 9. 部署与运维

```ini
# /etc/systemd/system/netmon.service
[Unit]
Description=Linux Network Traffic Monitor
After=network.target

[Service]
ExecStart=/usr/local/bin/netmon -c /etc/netmon/config.toml
Restart=on-failure
AmbientCapabilities=CAP_NET_RAW
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
```

运维要点：

- 日志：journald，按模块字段（module=parser）便于检索；
- 自身监控：收包 / 丢包 / 处理延迟 / 流表大小作为指标暴露，纳入告警；
- 备份：流记录定期导出，指标按保留策略自动清理；
- 升级：单二进制滚动替换，配置向后兼容。

## 10. 风险与演进路线

| 风险 / 约束 | 影响 | 应对 |
| --- | --- | --- |
| 抓包丢包 | 指标失真 | 环形缓冲调优、暴露丢包率、必要时 eBPF 前置过滤 |
| 流表内存膨胀 | 内存耗尽 | 双超时 + 流表上限 + LRU 淘汰 |
| eBPF 内核依赖 | 采集演进受限 | 首版 AF_PACKET 兜底，eBPF 作为可选加速 |
| 单机吞吐上限 | 无法覆盖大流量 | 多队列、CPU 绑定、采样降级，后续分布式采集 |
| 存储性能瓶颈 | 查询变慢 | 按规模分档升级存储后端，接口保持不变 |

演进路线：单机 MVP → 完整功能 → Agent + 中心聚合分布式架构 → DPI 与 NetFlow 接入。每一步都以第 5 章接口为边界，保证平滑演进。
