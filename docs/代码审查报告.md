## 二、高危（建议优先处理）

### H1 `-replay-file` 在没有 `source=replay` 时会静默地"跑合成流量"【确证 · **已在审查中修复**】

> **修复状态：已修复**
> 提交 `cd32fbe` — `fix(netmon): -replay-file 同时把数据源切到 replay`。
> `applyCLIOverrides` 现在在 `replayFile != ""` 时一并设 `cfg.Source = "replay"`（`cmd/netmon/main.go`）。
> `TestApplyCLIOverrides` 新增两条断言：给出 `-replay-file` 后 `source` 必须为 `replay`；未给出时不得改数据源。
> 端到端验证（配置文件**不含 `[core]` 段**，即默认 `synthetic`）：
> `netmon.exe -config config.toml -replay-file "<含空格的 pcap 路径>" -offline`
> → 启动日志 `source=replay ... offline=true`；回放结束后进程存活；
> `/api/v1/traffic/now` → 200（`bps=2833951.32 pps=636.50 conns=1915 source=replay version=0.23.0`）。

- 位置：`cmd/netmon/main.go` 的 `applyCLIOverrides`（本次 0.23.0 新增）
- 现象：`applyCLIOverrides` 在 `replayFile != ""` 时只覆盖 `cfg.ReplayFile`，**没有同时把 `cfg.Source` 设为 `"replay"`**。于是 `netmon.exe -replay-file x.pcap` 会以 `source=synthetic` 启动（配置默认值），**造包空跑**，`-replay-file` 被完全忽略，且不报任何错。
- 影响：这是 0.23.0 新增参数，**紧接着就会被 Windows 客户端用**（M3 落地路径就是"客户端用参数拉起采集端"）。用户会看到"跑起来了但数据不是我的 pcap"，极难自查——现象与 `[core]` 段被 BOM 吃掉（见 M13）几乎一样具有误导性。
- 修法（二选一）：
  1. `applyCLIOverrides` 中一并 `cfg.Source = "replay"`（**已采用**，符合"`-replay-file` 即等价于 source=replay + replay_file"的直觉）；
  2. 或显式报错：`-replay-file` 与 `source != "replay"` 同时出现时直接 `log.Fatalf`，要求用户显式声明。
- 附带（**仍未处理**）：`-offline` 同理——`offline=true` 而 `source != "replay"` 时，离线路径只在 replay 下有意义，建议报错或警告。

### H2 局域网无认证暴露全部管理接口（默认配置）【确证】

- 位置：`internal/api/api.go:119-121`
  ```go
  if s.cfg.APIToken != "" {
      h = requireToken(s.cfg.APIToken, h)
  }
  ```
- 现象：`APIToken`(即 `[api] token`) 为空时**整套鉴权中间件被跳过**。而 `Default()` 里 token 默认为空，`api.listen` 默认 `:8080`（**监听所有网卡**）。此时同网段任何机器都可以直接调用：
  - `POST /api/v1/actions/run`（执行服务端配置好的运维动作）
  - `POST /api/v1/actions/run` 触发抓包、`GET /api/v1/files/download`（下载白名单目录文件，见 H3）
  - `POST /api/v1/system/upgrade`（触发自升级）
  - `GET /api/v1/stream`（实时流量）
- 影响：这不是"代码写错"，而是**默认安全姿态过松**。项目定位是内网实验工具，所以危害有限，但用户很可能在宿舍/办公室 Wi-Fi 里就这么跑着。
- 修法（按代价从低到高）：
  1. 启动时若 `token == ""` 且 `listen` 不是回环地址，打印**醒目告警**（一行 `log.Printf`，零成本，建议至少做这个）；
  2. 默认监听收紧为 `127.0.0.1:8080`，需要跨机访问时再显式改成 `:8080`；
  3. 首次启动自动生成随机 token 并写入配置。
- 正面：**配了 token 之后鉴权本身是正确的**——`requireToken` 用 `subtle.ConstantTimeCompare` 常量时间比较，`/api/v1/stream` 单独校验（浏览器 `EventSource` 不能设请求头）也实现了，无绕过。

### H3 文件下载可经符号链接逃出白名单目录【确证】

- 位置：`internal/api/files.go:31-50`（`resolveUnderRoots`）+ `:113-135`（`handleFileDownload`）
- 现象：`resolveUnderRoots` 只做两件事——拒绝字符串 `..`、用 `filepath.Clean` 规范化路径，然后做前缀匹配：
  ```go
  target := filepath.ToSlash(clean)
  for _, root := range fileRoots {
      r := strings.TrimSuffix(filepath.ToSlash(filepath.Clean(root)), "/")
      if target == r || strings.HasPrefix(target, r+"/") {
          return clean, nil
      }
  }
  ```
  **`filepath.Clean` 不会解析符号链接，全程也没有 `filepath.EvalSymlinks`**。因此白名单目录里的一个 symlink 就能把下载引到任意文件：
  ```bash
  ln -s /etc/shadow /var/log/access.log     # 或 /root/.ssh/id_rsa
  curl 'http://host:8080/api/v1/files/download?path=/var/log/access.log'
  ```
  路径字符串 `/var/log/access.log` 完全通过校验；`http.ServeFile` 打开时会跟随 symlink，于是 `/etc/shadow` 被送出。
- 加重因素：文件通道默认白名单包含 `/etc` 与 `/home`，且**攻击者若能以低权限在 `/tmp` 落一个 symlink，就能读 root 文件**（`/tmp` 也在白名单里）。代码注释第 16 行明确写了"拒绝 `..` 与符号链接逃逸"，**但实现只做了前者**——属于文档与实现不一致。
- 修法：
  ```go
  real, err := filepath.EvalSymlinks(clean)   // 解析后重新做前缀校验
  if err != nil { /* 拒绝 */ }
  // 用 real 再跑一次白名单匹配，通过后才 ServeFile
  ```
  或改用 `os.Lstat` 拒绝任何 symlink（更严格，但会挡住 `/etc/ssl` 这类合法的软链目录）。
- 另建议：`fileRoots` 中的 `/etc`、`/home` 默认是否必要？按最小权限原则可考虑收窄。

### H4 客户端的「下载」按钮 = 用系统默认程序打开文件 → 一步代码执行【确证】

- 位置：`client/src/App.vue:894`（在 `downloadFile()` 内）
  ```js
  await openLocalFile(saved);
  ```
  → `client/src-tauri/src/lib.rs:296`
  ```rust
  std::process::Command::new("cmd").args(["/C", "start", "", path.as_str()]).spawn()
  ```
- 链路：服务端下发文件清单 → 用户点「下载」→ `saveServerFile` 落盘到 `%TEMP%\MeTD-files` → **紧接着自动打开它**。
- 关键点：`lib.rs:280-283` 的文件名白名单是 `c.is_alphanumeric() || "._-".contains(c)`，**扩展名被完整保留**。服务端只要把文件名起成 `report.pdf.exe`、`update.bat`、`x.cmd`、`y.lnk`、`z.scr`，客户端就会用 `cmd /C start` 交给系统关联程序**执行**。客户端↔采集端走**明文 HTTP**（`client/src/format.js` 无 scheme 时补 `http://`），因此链路上任何中间人或一台被伪冒的采集端，都能借"用户点一次下载"拿到用户权限的任意代码执行。
- 加重因素：
  - 下载目录固定 `%TEMP%\MeTD-files`（`lib.rs:278`），文件名**完全由服务端决定且无随机/去重**（`lib.rs:284`）→ 可覆盖上一次下载的同名文件，"以前下过、看起来可信"的文件也能被替换。
  - `open_local_file` 不做任何扩展名/类型判断。
- 修法：
  1. **删掉自动打开**，改成显式「打开」按钮 + 二次确认（这一条就能断掉整条链）；
  2. `open_local_file` 对 `.exe/.bat/.cmd/.com/.scr/.ps1/.lnk/.msi/.hta/.vbs/.js/.jse/.wsf/.reg` 一律拒绝，或改为"在资源管理器中定位"；
  3. 落盘目录加随机后缀防覆盖；下载后校验摘要。
- 正面：文件名的**路径穿越/ADS 防护本身是对的**——`lib.rs:280-283` 把 `..`、`/`、`\`、`:` 全变成 `_`，不会写出白名单目录。问题只在"下载完就执行"。

### H5 升级器的 URL 白名单用 `strings.HasPrefix` 校验原始字符串，可被 userinfo 绕过【确证】

- 位置：`internal/updater/updater.go:112-127`
  ```go
  parsed, err := url.Parse(raw)
  if err != nil || (parsed.Scheme != "http" && parsed.Scheme != "https") { return ErrURLNotAllowed }
  for _, p := range u.cfg.AllowedPrefixes {
      if p != "" && strings.HasPrefix(raw, p) { return nil }   // 比较的是 raw 原始串
  }
  ```
- 现象：匹配的是**未解析的原始字符串**，而不是 `parsed.Host`。设白名单为 `https://myhost/releases/`：
  - `https://myhost/releases/@evil.com/payload` → `parsed.Host` 仍是 `myhost`，OK；
  - `https://myhost/releases/../../..` 之类无效；
  - **真正的问题是反向利用**：若白名单写成 `https://myhost/`，`https://myhost@evil.com/payload` 也以该前缀开头，而 `url.Parse` 解析出的 `Host` 是 `evil.com` → 下载会打到攻击者主机。更现实的是 `http://` 与 `https://` 混写、或白名单只写到域名没带路径时，前缀匹配对 `myhost.evil.com` 同样成立（`https://myhost.evil.com/` 以 `https://myhost` 为前缀）。
- 危害被削弱的地方：下载后**强制校验 SHA256**（`updater.go:172-190`，`checksum` 必须由调用方提供 64 位十六进制），且校验 ELF 后才原子替换。所以攻击者要成功，需要同时控制白名单前缀允许的 URL **并** 让 `wantSHA` 与恶意文件匹配——若 SHA 来自配置（受信任），攻击者无法伪造内容。**因此这更像"纵深防御缺口 + 配置易踩坑"，而非可直接利用的 RCE。**
- 另：`u.client`（`updater.go` 内的 `http.Client`）**未设置 `CheckRedirect`**，默认允许最多 10 次跳转 → 一个通过白名单校验的 URL 可以被 302 到任意主机（内容仍受 SHA256 约束）。
- 修法：
  ```go
  // 用解析后的 Host + Path 做白名单，而不是原始串
  ep, _ := url.Parse(p)
  if parsed.Scheme == ep.Scheme && parsed.Host == ep.Host && strings.HasPrefix(parsed.Path, ep.Path) { ... }
  ```
  并设 `CheckRedirect` 拒绝跨主机跳转（或每跳重新校验白名单）。

### H6 插件目录加载：符号链接逃逸 + 单文件 64MB 全量读入内存【确证（大小上限）/ 推断（逃逸）】

- 位置：`internal/plugin/plugin.go:105`
  ```go
  raw, err := os.ReadFile(filepath.Join(dir, name))
  ```
- 现象 A（大小）：`os.ReadFile` **无任何大小上限**，一个几十 GB 的插件文件会直接 OOM。对比 `internal/api/files.go:19` 的 `maxDownloadBytes = 64 << 20`——下载通道有 64MB 上限，插件通道没有。
- 现象 B（逃逸）：`filepath.Join(dir, name)` 中的 `name` 若来自目录遍历（`os.ReadDir` 返回值，本身安全），则不会穿越；但若插件清单里的文件名可由外部配置/服务端指定，`.` 与 symlink 同样可绕过"仅限插件目录"的意图。**这一点需按实际调用方确认**（见第五节"存疑"）。
- 修法：读之前先 `os.Stat`/`os.Lstat` 校验 `Size() <= limit` 且非 symlink，再 `io.ReadAll(io.LimitReader(f, limit))`。

## 三、中危

### M1 SSE 流生命周期有洞 → 换服务器/换标签页后旧流继续跑，界面混入错误服务器的数据【确证】

**这是客户端最值得修的一条。**

- 位置：
  - `client/src/App.vue:1152-1166` `switchTab()`：saveCurrentTab → applyTabSnapshot → stopTimers → `await connect()`，**全程没有 `teardownStream()`**
  - `client/src/App.vue:1400-1401` `setupStream()` 开头 `if (streamStarted.value) return;`
  - `client/src/App.vue:1238-1295` `connect()` 内部**也不先停旧流**（只有 catch 分支才 `teardownStream`）
- 后果：从 A 服务器的标签页切到 B，`streamStarted` 仍为 `true` → `setupStream()` 提前返回 → Rust 侧 `start_stream` 不会被再次调用，而 `client/src-tauri/src/lib.rs:163-168` 的无限 loop 任务仍持有 **A 的 base + A 的 token**，继续把 A 的 `metd-snapshot` 经全局监听（`client/src/App.vue:1404-1415`）写进当前界面；与此同时 HTTP 轮询已经打到 B。用户看到的是 **"B 的界面 + A 的实时数据"**，而且 A 的令牌还在无人察觉的情况下被持续重连（`lib.rs:201` 是 3 秒退避的无限重试）。
- 同源第二条路径：`client/src/App.vue:1594-1600` `refreshNow()` 连续失败 4 次后只 `stopTimers()` + `connected=false`，**同样没有 `teardownStream()`**；随后从账号管理里重连另一台机器也会走 `setupStream` 的提前 return。
- 修法：`connect()` 开头无条件 `await teardownStream()`；`switchTab` 在 `connect()` 前也调一次；`refreshNow` 达失败阈值时一并 `teardownStream()`。

### M2 `withTimeout` 不取消底层请求、也不清定时器【确证】

- 位置：`client/src/App.vue:1226-1236`——只做 `Promise.race([promise, 超时 reject])`，既不 abort 底层 promise，也不 `clearTimeout`。
- 后果：
  1. 每次调用都留下一个最长到 `ms` 的悬挂定时器；
  2. **超时后请求仍在跑且仍会改状态**——例如 `connect()` 里的 `setConnection(...)` 超时后，Rust 侧 `*guard = Some(Conn{...})`（`client/src-tauri/src/lib.rs:49`）**仍会写入**，而前端已经走了失败分支；`apiGet("/api/v1/traffic/now")` 迟到的响应无人接管。
- 相关：`cancelConnect()`（`client/src/App.vue:1297-1306`）用 attempt 序号作废（`client/src/connect.js:24-26` `isCurrentAttempt`）只挡 UI 更新，挡不住已经发出的 Rust 调用，靠 `client/src/App.vue:1305` 的 `clearConnection().catch(() => {})` 补救，属 fire-and-forget。**取消的设计思路是对的，缺口在"超时/取消不中止在途工作"。**
- 修法：`withTimeout` 内 `clearTimeout`；给 Rust 命令加请求代次；`connect()` 每个 `await` 之后重新校验 attempt 并丢弃过期结果。

### M3 下载/抓包无大小上限、无清理【确证】

- 位置：`client/src-tauri/src/lib.rs:277` `resp.bytes().await` 一次性全读进内存，`:285` 直接 `fs::write`；`save_capture` 同理（`lib.rs:331`、`:339`）。无 `content_length` 校验、非流式。
- 后果：异常/恶意服务端或误点一个巨大日志文件即可 OOM 或写满 `%TEMP%`；`%TEMP%\MeTD-files`（`lib.rs:278`）与 `%TEMP%\MeTD-captures`（`lib.rs:332`）**从不清理**。
- 修法：超阈值（如 64MB，与服务端 `maxDownloadBytes` 对齐）拒绝；chunk 流式写盘；启动/下载前清理旧文件。

### M4 服务端返回的超大数组会让图表渲染抛 `RangeError`【确证】

- 位置：`client/src/components/TrafficChart.vue:250-251` `Math.max(1, ...bps)` / `Math.max(1, ...pps)`；`render()` 里 `client/src/components/TrafficChart.vue:318-321` 也用 `Math.max(0, ...pts.map(...))`。
- 实时路径的点数被 `client/src/livechart.js:3` 的 `LIVE_MAX_POINTS = 720` 限住，但 `refreshHistory()`（`client/src/App.vue:1603-1610`）的数组**完全来自服务端且无长度钳制**：返回十几万条即抛 `RangeError: Maximum call stack size exceeded`，渲染中断、图表卡死。
- 修法：`refreshHistory` 里 `slice(-N)`；`Math.max(...arr)` 改 `reduce`。

### M5 `handleHistory` 的 `since`/`step` 无上界，可被一条请求打满内存【确证】

- 位置：`internal/api/api.go:197-217`
  ```go
  since := intParam(r, "since", 3600)
  step  := intParam(r, "step", 60)
  if step < 1 { step = 1 }
  ...
  n := int(to.Sub(from).Seconds())/step + 1
  rows := make([]point, n)          // 立即按 n 分配
  ```
- 现象：`step` 只钳了下界，`since` **完全没有钳制**（也没有上界），`intParam` 也不限幅。`?since=2147483647&step=1` 会让 `n` 达到 21 亿 → `make([]point, n)` 单次分配几十 GB，直接 OOM；即使不 OOM，循环遍历 5 个序列 × 21 亿索引也会把 CPU 打满。
- 修法：`since` 钳到合理上界（如 ≤ 30 天或 ≤ `retention_hours`），`step` 给下界之后再加一个"点数上限"（如 `n > 10000` 时自动放大 `step` 或返回 400）。

### M6 `handleSessions` 的 `port` 无上界检查，`uint16` 静默截断【确证】

- 位置：`internal/api/api.go:286-288`
  ```go
  if p, err := strconv.Atoi(q.Get("port")); err == nil && p > 0 {
      f.Port = uint16(p)          // p=70000 → 4464
  }
  ```
- 现象：`?port=70000` 被静默截断为 `4464`，用户以为在查 70000 端口、实际查的是 4464，**返回结果看起来"正常"但语义是错的**（这类静默错值最难排查）。应 `p > 65535` 时返回 400。
- 附带：`intParam`（`internal/api/api.go`）对非数字输入静默回退默认值，也是同类"静默降级"风格，建议至少记一条 debug 日志。

### M7 告警模块在持锁状态下发起网络请求【推断，附验证方式】

- 审查线索指向 `internal/alert/`：投递（webhook 等）与状态更新共用同一把锁，网络请求在锁内执行。
- 后果：慢/挂死的对端会让整条告警链路（以及所有等待该锁的调用方）一起阻塞；采集侧若在报文处理路径上同步调用，表现为**采集卡顿**。
- 验证方式：`go test -race -count=1 ./internal/alert/` + 阅读 `Send`/`dispatch` 的锁范围；把"取快照 → 解锁 → 网络请求 → 重新加锁记录结果"改造成两段式即可。
- **本条为静态推断，尚未逐行确证**，处理前请先核实。

### M8 `main` 无法区分正常结束与异常结束，且未 flush 在线路径的残留会话【确证】

- 位置：`internal/app/app.go`（`runOnline` 收尾）+ `cmd/netmon/main.go:132-143`
- 现象 A：`main` 收到 `runErr` 后只打日志（`:137-140`，`err == nil` 时连日志都不打），随即 `Shutdown` + 退出——**没有区分"源正常结束"与"源出错"**。0.23.0 已把非 `io.EOF` 源错误透出，但 `main` 侧仍未据 err 设置退出码（`os.Exit(1)`）。
- 现象 B：`runOnline` 在通道关闭时排空缓冲后直接返回，**不像 `runOffline` 那样 `flushRemaining()`** → 在线模式退出时，仍未过期的 active 会话不会被落盘。
- 修法：`main` 用 `errors.Is` 区分 `io.EOF` 与其它错误并设置退出码；`runOnline` 收尾也调用一次收尾 tick + `flushRemaining()`。

### M9 `defer` 在 `log.Fatalf`（`os.Exit`）路径上不执行，资源不释放【确证】

- 位置：`cmd/netmon/main.go:63` `defer src.Close()`、`:76` `defer store.Close()`
- 现象：任何走 `log.Fatalf` 的路径都会**跳过所有 defer**（`os.Exit` 不跑 defer）→ 文件句柄/套接字不关闭。实测中表现为 `FileStore` 未 `Close` 导致临时目录清理失败：`unlinkat ...\flows.jsonl: The process cannot access the file because it is being used by another process.`
- 修法：把 `log.Fatalf` 换成"记录错误 + 设置退出码 + 走到函数末尾 `return`"，或把关键清理显式调用。

### M10 客户端「关闭到托盘」后仍全速轮询/推流；`onCloseRequested` 的 Promise 没人接【确证】

- 位置：`client/src/App.vue:1668` `appWindow.onCloseRequested(async (event) => {...})` 返回值未被 `await`/`catch`，回调里的 `await appWindow.hide()` 失败会产生**未处理 rejection**。
- 该回调只做 `event.preventDefault()` + hide，**没有 `stopTimers()`、没有 `teardownStream()`**；而 `closeToTray` 默认 `true`（`client/src/settings.js:28`），于是窗口一隐藏，五个定时器（`client/src/App.vue:1530-1541`：1s / 2s / 8s / 5s / 10s）与 SSE 长连接继续常驻。
- 修法：hide 前 `stopTimers` + `teardownStream`（显示时恢复），`onCloseRequested` 补 `.catch`。

### M11 `onBeforeUnmount` 清理不完整【确证】

- 位置：`client/src/App.vue:1681-1684` 只 `stopTimers()` + `clearTimeout(toastTimer)`。
- 遗漏：`filterTimer`（`client/src/App.vue:1631-1638` 的 400ms 防抖）、SSE 的两个 unlisten 句柄（`client/src/App.vue:1395-1419` 存下 `unlistenSnapshot` / `unlistenAlert` 后**从未调用**）、以及 `teardownStream()`（Rust 侧 SSE 任务会一直重连到进程退出）。

### M12 多机探测会把每台档案的明文令牌发到其 base【确证，属设计取舍】

- 位置：`client/src/App.vue:720-734` `probeAllHosts()` 把 `{name, base, token}` 交给 `probeHosts`；Rust 侧 `client/src-tauri/src/lib.rs:222-238` 逐个用该令牌请求（HTTP 明文）。
- 设计如此（多机监测必须用各自凭据），**但档案列表里只要有一条外部/不可信地址，令牌就会被明文送到那里**。
- 修法：限制自动探测只对已确认的内网地址生效，或在 UI 明确标注"探测会向该地址发送其令牌"。

### M13 UTF-8 BOM 会让整个 `[core]` 段被静默丢弃【确证，实测踩到】

- 位置：`internal/config/config.go` 的 `Load`——`strings.TrimSpace` **不剥 U+FEFF**，首行 `"\uFEFF[core]"` 匹配不上 section 头 → 整段 `core.*` 失效。
- 触发条件：用 Windows PowerShell 5.1 的 `Set-Content -Encoding utf8`（会写 BOM）或带 BOM 的编辑器生成 `config.toml`。实测中 netmon 因此退回 `source=synthetic` **空跑 40 秒且不报错**，现象酷似"部署成功但没数据"。
- 影响：M3 落地后 Windows 客户端很可能要生成/写回配置，这条会真实复现。
- 修法：`Load` 开头 `strings.TrimPrefix(data, "\uFEFF")`（一行）。

### M14 `live_other.go` 的 build tag 是 `!linux`，新增 `live_windows.go` 会编译失败【确证】

- 位置：`internal/capture/live_other.go:1` `//go:build !linux`
- 现象：`!linux` 在 **Windows 上也成立**。若按《双模式设计文档》的计划新增 `live_windows.go` 实现 `NewLive`/`NewLiveWithReaders`/`NewLiveWithReadersPinned`，会与 `live_other.go` **重复定义** → 编译失败。
- 修法：先把 `live_other.go` 改成 `//go:build !linux && !windows`，再加 `live_windows.go`（`//go:build windows`）。
- 现状：全仓只有 4 个 build tag 文件（`live_linux.go`:1 `//go:build linux`、`live_other.go`:1 `//go:build !linux`、`internal/updater/exec_unix.go`:1 `//go:build !windows`、`exec_windows.go`:1 `//go:build windows`），当前互斥关系是正确的。
